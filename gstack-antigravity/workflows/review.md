# /review — 코드 리뷰

CI가 통과하는 건 아무 의미 없다. 프로덕션에서 터지는 버그를 찾는 게 리뷰다.

---

## Step 1: 변경사항 파악

```bash
git diff --stat
git diff --name-only
git log --oneline -10
```

변경된 파일 목록, 변경량, 최근 커밋 히스토리를 파악한다.

---

## Step 2: Diff 분석

변경된 모든 파일의 diff를 읽는다. 파일 하나씩.

각 변경에 대해 분류:

| 분류 | 의미 | 행동 |
|------|------|------|
| 🔴 BUG | 프로덕션 버그 | 즉시 수정 |
| 🟡 ISSUE | 잠재적 문제 | 사용자에게 질문 |
| 🟢 NIT | 스타일/사소한 것 | 모아서 한번에 언급 |
| ✅ GOOD | 잘한 것 | 인정 (1-2개만) |

---

## Step 3: 프로덕션 버그 패턴 체크

### 필수 체크 항목:
- [ ] **에러 핸들링**: try/catch 누락, 에러 삼킴, 구체적이지 않은 catch
- [ ] **Null/Undefined**: 옵셔널 체이닝 누락, 타입 가드 없음
- [ ] **경쟁 조건**: async/await 누락, 공유 상태 동시 변경
- [ ] **보안**: 사용자 입력 미검증, SQL 인젝션, XSS
- [ ] **성능**: N+1 쿼리, 불필요한 리렌더, 메모리 누수
- [ ] **엣지 케이스**: 빈 배열, 빈 문자열, 0, null, 매우 긴 문자열
- [ ] **테스트**: 새 로직에 테스트 있는가, 엣지 케이스 커버하는가

---

## Step 4: 자동 수정 vs 질문

### AUTO-FIX (바로 고침):
- 오타
- 불필요한 import
- 명확한 타입 에러
- 빠진 await
- console.log 제거

### ASK (사용자에게 물어봄):
- 로직 변경이 필요한 버그
- 아키텍처 결정이 필요한 것
- 의도가 불분명한 코드

---

## Step 5: 완성도 감사

```
╔═══════════════════════════════════════╗
║          REVIEW REPORT                ║
╠═══════════════════════════════════════╣
║ 파일 리뷰:    N/N개 완료              ║
║ 🔴 BUG:       N개 (AUTO-FIX: N)      ║
║ 🟡 ISSUE:     N개 (ASK: N)           ║
║ 🟢 NIT:       N개                    ║
║ 테스트 커버:  추가 필요 / 충분        ║
╠═══════════════════════════════════════╣
║ 판정: APPROVE / REQUEST_CHANGES      ║
╚═══════════════════════════════════════╝
```

### APPROVE 조건:
- 🔴 BUG가 0개
- 모든 🟡 ISSUE에 대해 사용자 확인 완료
- 새 로직에 테스트 존재

### REQUEST_CHANGES:
- 🔴 BUG 존재
- 미해결 🟡 ISSUE 존재
- 테스트 없는 새 로직

---

## 완료 상태
- **DONE** — 모든 파일 리뷰 완료, BUG 없음
- **DONE_WITH_CONCERNS** — 완료했지만 주의 필요한 ISSUE 있음
- **BLOCKED** — diff가 너무 크거나 컨텍스트 부족

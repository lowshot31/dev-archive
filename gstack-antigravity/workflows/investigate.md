# /investigate — 체계적 디버깅

## 🔴 철의 법칙
**근본 원인 조사 없이 수정 없음.**
증상을 고치면 두더지 잡기 디버깅이 된다. 원인을 찾고, 그 다음에 고친다.

---

## Phase 1: 근본 원인 조사

### 1.1: 증상 수집
- 에러 메시지, 스택 트레이스, 재현 단계 정리
- 정보 부족하면 사용자에게 **하나씩** 질문

### 1.2: 코드 읽기
- 증상에서 잠재적 원인까지 코드 경로 역추적
- `grep`으로 관련 참조 전부 찾기
- `view_file`로 로직 이해

### 1.3: 최근 변경 확인
```bash
git log --oneline -20 -- <영향받은_파일들>
git diff HEAD~5 -- <영향받은_파일들>
```
예전에 되던 거면? 원인은 diff에 있다.

### 1.4: 재현
결정적으로 재현 가능한가? 불가능하면 Phase 2 전에 증거를 더 모은다.

---

## Phase 2: 패턴 분석

| 패턴 | 시그니처 | 어디를 볼 것 |
|------|----------|-------------|
| 경쟁 조건 | 간헐적, 타이밍 의존 | 공유 상태 동시 접근 |
| Null 전파 | TypeError, undefined | 옵셔널 값 가드 누락 |
| 상태 오염 | 일관성 없는 데이터 | 트랜잭션, 콜백, 훅 |
| 통합 실패 | 타임아웃, 예상 밖 응답 | 외부 API, 서비스 경계 |
| 설정 드리프트 | 로컬 OK, 스테이징 실패 | 환경변수, 피처 플래그 |
| 캐시 문제 | 오래된 데이터 표시 | Redis, CDN, 브라우저 캐시 |

---

## Phase 3: 가설 테스트

### 3-Strike Rule ⚠️
1. **가설 확인:** 의심 지점에 임시 로그/어서션 추가. 재현 실행. 증거가 맞는가?
2. **가설이 틀리면:** 웹 검색으로 유사 사례 확인 (민감 정보 제거 후). Phase 1로 돌아가서 증거 추가 수집. 추측 금지.
3. **3번 실패하면 → STOP.**

```
3개 가설 테스트 완료, 전부 불일치.
단순 버그가 아니라 아키텍처 문제일 수 있음.

A) 계속 조사 — 새로운 가설: [설명]
B) 사람한테 에스컬레이션 — 시스템을 아는 사람이 필요
C) 로깅 추가하고 대기 — 계측 설치 후 다음 발생 시 잡기
```

### 레드 플래그 (이게 보이면 멈춘다)
- "일단 임시로 고치자" → 임시는 없다. 제대로 고치거나 에스컬레이션.
- 데이터 흐름 추적 전에 수정 제안 → 추측이다.
- 수정할 때마다 다른 곳에서 문제 발생 → 잘못된 레이어를 보고 있다.

---

## Phase 4: 구현

근본 원인이 확인되면:

1. **원인을 고친다. 증상이 아니라.** 문제를 실제로 제거하는 최소 변경.
2. **최소 diff.** 파일 적게, 라인 적게. 인접 코드 리팩토링 충동 참기.
3. **회귀 테스트 작성:**
   - 수정 없이 **실패** (테스트가 의미 있음을 증명)
   - 수정 후 **통과** (수정이 작동함을 증명)
4. **전체 테스트 스위트 실행.** 출력 붙여넣기. 회귀 없음 확인.
5. **5개 파일 이상 수정 시** → 사용자에게 블래스트 레이디어스 확인.

---

## Phase 5: 검증 & 보고

원래 버그 시나리오 재현 → 수정 확인. 이건 선택이 아님.

```
디버그 리포트
════════════════════════════════════════
증상:         [사용자가 관찰한 것]
근본 원인:    [실제로 뭐가 잘못됐는지]
수정:         [뭘 바꿨는지, 파일:라인 참조]
증거:         [테스트 결과, 재현 시도]
회귀 테스트:  [파일:라인]
관련:         [같은 영역의 이전 버그, 아키텍처 노트]
상태:         DONE | DONE_WITH_CONCERNS | BLOCKED
════════════════════════════════════════
```
